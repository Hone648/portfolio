## The problem

newBudget exists because monthly financial planning was fragmented across too many places at once. Income lived in one view, recurring obligations somewhere else, debt payments with whoever was owed, and day-to-day spending usually appeared only after the bank had already recorded it.

Each source could be accurate on its own, but none of them answered the practical question I needed every few weeks: what does this month look like?

The product starts from that question. A month needs to show what is available, what is due, what has already been paid, what remains outstanding, and what should carry into the next month. I built newBudget as a privately operated production application so those pieces could be planned and reviewed together instead of reassembled by hand.

## Three engineering decisions

Three engineering decisions shaped how newBudget handles planning, financial consistency, and ownership.

<ol aria-label="High-signal engineering decisions">
  <li>
    <strong>The month is the workspace</strong>
    <p>The selected month is the organizing context for income, carryover, recurring obligations, bills and expenses, payment state, and remaining balance. Future recurring obligations can be previewed deterministically on the read path without immediately creating persisted monthly rows; a real owned record is written only when the user takes an action that requires one.</p>
  </li>
  <li>
    <strong>Money is modeled for consistency</strong>
    <p>Currency uses integer minor units instead of floating-point arithmetic, and rates use integer basis-point semantics where applicable. Installment history is represented through ordered monthly snapshots so later estimated balances can be recalculated when earlier payment history changes. The result is a consistent planning model, not creditor-exact accounting or financial advice.</p>
  </li>
  <li>
    <strong>Ownership is resolved on the server</strong>
    <p>Google/Auth.js establishes authenticated identity, but the domain records a stable internal application-user owner. The browser can request a resource; it cannot nominate authoritative ownership. Server-side access combines the requested resource with the authenticated internal owner, and production fails closed without valid authenticated context.</p>
  </li>
</ol>

## Supporting product views

The month-first workspace is the center of the product, but planning also needs longer-running context. The supporting views aggregate spending by category and show debt and payment history across selectable periods, so the monthly view is not disconnected from trends over time.

Those outputs are intentionally framed as planning information. They demonstrate implemented product behavior, not audited reporting, lender statements, or lender-exact balance accounting.

## Production lesson

The strongest operational lesson came from a carryover defect in production. A later month brought forward the wrong amount because the code walked back through prior months as though a persisted monthly-statement document existed. Many real production months are synthesized from underlying activity instead, so the original tests covered a convenient shape rather than the shape production often used.

The fix added the missing production-shaped case: synthesize eligible prior months from their underlying activity when no persisted statement exists, and carry forward the same due-basis remaining value the workspace displayed. The stored financial records did not need to be edited; the problem was in derivation.

The release still was not finished. The fix passed validation and deployed successfully, but the canonical production URL continued serving the older behavior because its alias still resolved to a previous build. Correcting the alias surfaced production authentication configuration issues, so I kept a known-working deployment available while generating and verifying the clean deployment.

> A green build and a successful deployment do not prove that the canonical production domain is serving that build.

Verifying the exact build behind the canonical production domain is now part of the release process, alongside code validation, authenticated route checks, and product-path review.
