## Why I built a local security and automation hub

A camera that alerts on motion alerts on everything: wind moving a branch, headlights sweeping past, rain, a cat. Repeated low-value notifications make the alert stream easy to ignore — precisely the outcome I wanted to avoid.

The question I wanted answered was narrower: not "did something change in this frame," but "did a person appear somewhere that matters, at a time when it matters." That is what this system is built around.

I also wanted the answer produced locally. Video from around a home is about as sensitive as personal data gets.

So this became a working residential system rather than an architecture sketch. I chose and integrated the services, brought the cameras in, configured and validated the event path, worked through the failures, and decided where public explanation stops. It is operational in a private residence: useful in practice, and not a commercial security product or a professionally monitored alarm.

## Designing one event path across separate systems

It helps to follow a single event from the camera to the phone, because no one service owns the outcome.

A camera produces video. RTSP carries it to the host. Frigate receives the streams, records locally, and runs object detection, with a Google Coral Edge TPU handling the accelerated inference workload — which is what makes continuous detection on a modest single host practical. When Frigate classifies an object it emits an event, and this workflow selects the `person` class from Frigate's broader output. That event goes to Home Assistant, which decides whether the configured area and time context make it worth interrupting someone. If so, Home Assistant sends the mobile notification, and the loop ends there.

Every handoff is both a decision point and a place where things can quietly stop working. Reading the system as one path rather than a stack of installed software is what makes everything below easier to follow.

## Treating detection as an input, not a decision

The most useful choice I made was refusing to let detection be the alert.

Motion is the crudest signal: something in the frame changed. A classified object event is better — Frigate says this looks like a particular kind of object, and selecting the `person` class narrows further. But even a confident person event is only a candidate: it answers what Frigate saw, not whether I need to know about it.

That second question belongs to Home Assistant, and it is policy rather than detection. The event has to correspond to a configured area, and the time has to fall inside an approved automation window, before the notification action runs. Where and when carry as much meaning as what — the same person in the same spot can be unremarkable at one hour and worth a look at another.

Splitting those responsibilities keeps the alerts worth reading. It does not make them correct: false positives still happen, meaningful events can still be missed, and I have not measured a detection rate. The system also does not identify anyone — it classifies object types, which is not facial recognition or biometric identification.

## Bringing three camera streams into the local hub

Three RTSP streams currently feed Frigate for local recording and detection. Integrating them was less about configuration syntax than about learning where things break.

A camera has to be reachable on the local network and accept authentication. Its stream has to actually be served, in a form the ingesting service can consume. The host has to reach it, and so does the container — not automatically the same statement. And Frigate has to accept the configuration describing it.

The lesson that stuck is that one visible symptom covers all of those. A blank camera tile tells you the picture is missing. It does not tell you whether the camera is offline, authentication is failing, the stream is not being served, the container cannot reach what the host can, or the configuration is being rejected before the stream is attempted. Reading that as "the camera is broken" is how you end up power-cycling hardware that was fine the whole time.

## Using service boundaries to keep the system understandable

Frigate, Home Assistant, and Mosquitto run as separate containerized services on one Ubuntu Server host. That separation is what makes the system debuggable by one person.

Frigate ingests streams, records, and produces object events. Home Assistant evaluates conditions and takes actions. Mosquitto carries local publish-and-subscribe messaging. Because they are separate, each has its own logs and health, and I can inspect or restart one without treating the hub as a single opaque application.

MQTT is worth describing at that architectural level: a producer, a broker, and consumers, so an event source does not have to know who is listening. Verifying local MQTT messaging was part of bringing the hub together, and an observable message boundary helps when diagnosing integration. Broker details, topics, payloads, identifiers, and credentials stay unpublished, and not every automation here depends on a hand-authored topic — the point is that the messaging layer exists, works locally, and can be inspected on its own.

What container separation does not give me is orchestration beyond Docker on one host: no failover, no self-healing, no distribution, no formal observability stack.

## Troubleshooting the path one boundary at a time

The most revealing failure mode is the boring one — the notification that never arrives.

"Container running" is a process fact, not an end-to-end result. Frigate can be running while a camera stream is dead. A stream can be visible while no object events are produced. An object event can exist while it falls outside the configured area or time policy. The automation can fire while the notification never lands. All four produce the same outcome: nothing happened, and the temptation is to start changing things — restart a service, edit a condition, reboot the host — and then have no idea which change mattered.

The method that replaces guessing is to walk the path in order. Start at the nearest observable input and confirm it receives what it should. Confirm it produces what the next boundary expects. Move one step downstream. Where the expected output disappears, stop: that is the layer to diagnose, and everything past it is a symptom.

For a missing alert that means checking, in order: the camera is reachable, the stream is being served, the host and then the container can get to it, Frigate is ingesting it, a selected object event is produced, local messaging is moving where it applies, Home Assistant's conditions evaluate the way I think they do, and the notification action ran and delivered.

Most of the value is in the ordering. It keeps a stream problem from being debugged as an automation problem, and keeps me from editing an automation that was never reached.

## Operating a local system without pretending it is highly available

Local-first is a real tradeoff, not a free win.

The upside is direct ownership: recording and inference happen on hardware I control, and the event path is mine to change. The cost is that everything operational is also mine — updates, storage, networking, service health, and recovery. One host keeps integration simple, and it is also a single dependency underneath the whole detection-and-alert path.

The honest summary: the system is operational and I use it, with no measured availability figure, no failover, and no validated recovery process. The mobile notification is an alert for me to look at — not professional monitoring, not redundant paging, not emergency dispatch, and not something whose delivery is promised. Running the core services locally is also not the same as proving every dependency is fully offline.

## Keeping useful evidence from becoming a security disclosure

Almost everything that would make this case study more impressive would also make a house less safe.

Home-security infrastructure is unusually revealing. Footage shows people and property. Camera placement and coverage show how a property is watched, and where it is not. Zone names and automation windows describe when someone expects to be alerted — close to describing when anyone is home. Network layout, credentials, and messaging details describe how to interfere with it. Individually these look like ordinary technical detail; together they are a map.

That is why there are no frames, clips, or configuration here, and why exact areas, schedules, addresses, identifiers, and stream details stay out of it. It is also why this project deliberately has no public repository and no live link. An older home-automation repository of mine exists, but it does not represent this deployment.

What is publishable is the reasoning: the event path, the responsibilities, the policy decision, the failure boundaries. Withholding the rest is a decision about what is safe to say, not evidence that the deployment is hardened or audited.

## How I built and validated the system

I brought this up incrementally, because a system assembled all at once fails all at once.

Each service went in with its responsibility understood and checked before the next depended on it: the host and containers, then a stream at a time into Frigate, then local MQTT messaging verified as flowing, then object events confirmed to be produced and classified, then automation conditions tested against events I could reproduce, and finally the mobile notification confirmed to arrive. Logs and service health showed what each boundary was receiving and emitting. Every configuration change was one I made and reviewed by hand.

AI assistance helped with research, troubleshooting ideas, documentation, and implementation guidance. The requirements, deployment and configuration decisions, physical work, diagnosis, validation, and privacy boundaries were mine, and nothing administered the live system on its own.

## What this project demonstrates

This is the project where the pieces I care about stop being separate subjects.

It runs across software, networking, hardware acceleration, and physical devices, and the interesting work is at the joints: one event path across independent services, detection treated as an input rather than a verdict, and alert policy placed where context lives instead of where classification happens. It taught me to think in boundaries — what each layer receives, what it emits, and which one to interrogate when the result is missing.

It also taught me what a locally operated system asks of the person running it, and where public explanation has to stop when the subject is a home.

What it is not is professional security work. Three cameras in a residence is an integration, not a commercial deployment. Selective notifications are useful, not certified detection. Running well is not the same as measured availability.
