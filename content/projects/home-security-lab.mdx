## The problem

I wanted a home security stack whose behavior I could inspect and operate myself. That made local processing, understandable boundaries, and reviewable configuration more important than a polished appliance abstraction.

The operational system runs in a private residential environment on an Ubuntu 24.04.3 LTS host with Docker Compose, Frigate, Home Assistant, and Mosquitto. The public `nvr-infrastructure` repository contains sanitized representative documentation and configuration; it is evidence of the architecture and operating practices, not a verbatim private deployment.

This is an operational systems-integration project. It is not a commercial security product, professionally monitored alarm, emergency-response system, enterprise video platform, highly available service, fully offline system, air-gapped environment, or guaranteed intrusion-detection claim.

The engineering value is not that several containers run together. It is that the stack has an inspectable event path, a reviewed source boundary, and documented operating procedures that are kept separate from claims about what has actually been exercised on the private system.

That keeps troubleshooting tied to observable boundaries rather than service names or dashboard health alone.

## Three engineering decisions

<ol aria-label="High-signal engineering decisions">
  <li>
    <strong>Troubleshoot the event path, not the containers</strong>
    <p>The useful abstraction is the event path: sanitized RTSP inputs feed Frigate video processing and detection events, MQTT carries the event through Mosquitto, Home Assistant consumes it, and a representative persistent-notification action proves the boundary in public source. A running container alone does not prove that every upstream input, broker handoff, consumer rule, or action is healthy.</p>
  </li>
  <li>
    <strong>Reviewed configuration is source</strong>
    <p>The repository tracks selected sanitized Compose, Frigate, Home Assistant, and Mosquitto configuration. It excludes credentials, authenticated stream material, private identifiers, runtime data, logs, databases, recordings, and access details. Validation tooling checks YAML syntax, the Python validator, Bash syntax, the Compose model, and Mosquitto configuration before changes are treated as ready for the private operational copy.</p>
  </li>
  <li>
    <strong>Documented procedures stay distinct from exercised operations</strong>
    <p>Implemented or reviewed evidence includes repository validation tooling, the current Frigate age- and event-oriented retention setup, and the private stack's operational event path. Backup-before-replacement, repository-to-live deployment, targeted service recreation, post-deployment verification, and configuration rollback are documented procedures without separate evidence that they have been exercised against the live stack. Full backup and tested recovery, monitoring and maintenance automation, disk-threshold cleanup, security hardening, and network rework remain planned. An exact image-pinning policy exists, but exact pinning remains incomplete.</p>
  </li>
</ol>

## Privacy boundary

There is no portfolio-hosted visual gallery for this project because residential security evidence can reveal access paths and household patterns even when it looks harmless. The public evidence is sanitized source and documentation. It does not publish footage, camera views, private identifiers, credentials, schedules, access material, recordings, or internal network layout.

That boundary lets the project remain reviewable without turning publication into a security audit. The public repository demonstrates selected configuration shape, validation practice, and operating discipline while keeping the private deployment private.

For a residential security system, screenshots can expose more operational detail than they prove. Sanitized source provides a safer evidence boundary: enough to review configuration shape and operating discipline without publishing sensitive context.

## What this project demonstrates

The project shows practical systems integration: Frigate handles video and detection work, Mosquitto carries events, and Home Assistant consumes the relevant flow for automation. It also shows the difference between running services and operating a system. A useful stack needs source review, validation, documented change handling, honest privacy limits, and clear language about what evidence proves.

The strongest claim here is disciplined operational clarity. The stack works in a private residential context, the public repository supports review of selected sanitized configuration, and the roadmap items stay in the future tense until they have separate evidence.
